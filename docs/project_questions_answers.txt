100 вопросов и ответов по проекту Apex Stats

Раздел 1. Теоретические вопросы - 30

1. Что представляет собой проект Apex Stats?
Ответ: Apex Stats - это web-платформа для просмотра и анализа статистики матчей Apex Legends. В текущем проекте есть пользовательские страницы с турнирами, матчами, играми, картами и командами, а также административные страницы для управления справочными данными, пользователями и результатами обработки.

2. Какую основную задачу решает система?
Ответ: Система связывает данные о турнирах, матчах, командах, картах, игроках и результатах обработки видео в едином интерфейсе. Она позволяет не только просматривать статистику, но и открывать обработанные JSON-результаты конкретных игр, включая тестовые матчи.

3. Почему проект разделен на web-интерфейс и локальные скрипты обработки видео?
Ответ: Web-интерфейс отвечает за просмотр данных и администрирование, а тяжелая обработка видео вынесена в локальные Python-скрипты. Это сделано потому, что анализ VOD требует OpenCV/ML-зависимостей, доступа к видеофайлам и вычислительных ресурсов, которые не нужны для обычного просмотра сайта.

4. Почему результаты анализа сохраняются в JSON?
Ответ: JSON удобно читать в браузере без дополнительной серверной обработки. В проекте результаты матчей, треки, кольца, события HUD и другие артефакты лежат в структурированных JSON-файлах в `src/data/<game>/` или в папках `scripts/tracking/matches/<video-stem>/`.

5. Что означает локальная обработка в контексте проекта?
Ответ: Локальная обработка означает, что видеоаналитика запускается на ПК пользователя, а не на VPS и не в облаке. На сервер или в статическую сборку попадают только уже подготовленные данные и web-интерфейс, без тяжелых видеофайлов и промежуточных артефактов.

6. Почему для видеоаналитики важна модульная архитектура?
Ответ: В проекте разные этапы обработки выполняют разные задачи: поиск нарезок, поиск плашек, распознавание тегов, чтение HUD, поиск колец и постобработка. Модульность позволяет заменять или архивировать отдельные эксперименты без переписывания всего пайплайна.

7. Что такое плашка команды в задаче анализа видео?
Ответ: Плашка команды - это визуальный элемент на кадре трансляции, по которому можно определить команду или слот команды. В проекте для этого есть модули `detect_plates` и интегрированный `plate_detector`, а результаты используются для построения траекторий.

8. Почему в идентификации команды используется несколько признаков?
Ответ: Один признак может быть ненадежным: цвет может быть похожим у разных команд, плашка может быть частично закрыта, а позиция может меняться из-за камеры. Поэтому проект учитывает цветовые профили, размеры, список команд матча, стартовые зоны и историю положения.

9. Зачем нужна каноническая карта?
Ответ: Каноническая карта дает стабильную систему координат, не зависящую от зума и панорамирования камеры наблюдателя. В `tracks.json` для этого хранятся координаты на канонической карте и данные о положении камеры.

10. Что такое гомография в контексте проекта?
Ответ: Гомография используется как способ сопоставить изображение карты в кадре с канонической картой. В документации tracking-lab указано, что такой подход нужен, чтобы зум и панорамирование наблюдателя не ломали координаты.

11. Зачем нужен трекинг команд во времени?
Ответ: Трекинг позволяет получить не только отдельные точки на кадрах, но и последовательность перемещения команды по карте. Это нужно для просмотра траекторий, анализа перемещений и восстановления положения команды после временной потери детекции.

12. Почему история положения помогает распознавать команды?
Ответ: Если команда уже была найдена в предыдущих кадрах, ее последнее известное положение можно использовать как дополнительную подсказку. Это снижает вероятность перескока идентификатора на похожую по цвету команду.

13. Для чего в проекте нужны стартовые зоны команд?
Ответ: Стартовые зоны используются как позиционная подсказка в начале матча. Если алгоритм сомневается между командами, знание ожидаемой зоны высадки помогает выбрать более вероятное соответствие.

14. Почему вес стартовой зоны должен уменьшаться со временем?
Ответ: По мере развития матча команды уходят из стартовых областей, поэтому начальная подсказка становится менее актуальной. В требованиях проекта это описано как убывание веса стартовой зоны по экспоненте от времени матча.

15. Что такое HUD-анализ в проекте?
Ответ: HUD-анализ относится к чтению информации из интерфейса трансляции: таймлайна, колец, eliminations и других событий. В проекте за это отвечает модуль `scripts/tracking/modules/hud_read`.

16. Зачем проекту отдельная страница Tracking Lab?
Ответ: Tracking Lab нужен для визуальной проверки результатов обработки VOD. Согласно документации, туда можно загрузить `tracks.json` и, при необходимости, видео, чтобы смотреть треки команд на канонической карте и скрабить по таймлайну.

17. Почему в проекте есть тестовая игра `/games/m-test-g1`?
Ответ: Эта игра оставлена как тестовая для просмотра подготовленных JSON-результатов в MatchViewer. В коде есть отдельная логика, которая считает `m-test` и `m-test-*` тестовыми матчами и исключает их из публичных подсчетов.

18. Что такое tier-list карт и оружия в проекте?
Ответ: Это агрегированное представление статистики по картам и оружию для команд. В проекте есть snapshot-файлы `algs-team-rosters.snapshot.json` и `algs-team-weapons.snapshot.json`, а страницы команд используют эти данные для состава, карт и weapon meta.

19. Почему фотографии игроков были вынесены в локальные WebP-файлы?
Ответ: Изначально внешние изображения могли быть тяжелыми и замедлять загрузку. В проекте есть локальная папка `public/player-images/` и manifest `src/data/player-images.manifest.json`, что позволяет использовать оптимизированные WebP-изображения.

20. Чем отличаются пользовательские страницы от админки?
Ответ: Пользовательские страницы предназначены для просмотра: команды, турниры, матчи, карты и игры. Админка содержит инструменты управления данными, пользователями, калибровками, процессами анализа, HSV, POI, полигонами и Tracking Lab.

21. Почему права доступа разделены на роли?
Ответ: В проекте есть роли `user`, `operator` и `administrator`, а доступ проверяется через ранги ролей. Это позволяет отделить обычный просмотр от операторских страниц и административного управления пользователями.

22. Зачем нужна invite-ссылка?
Ответ: Invite-ссылка позволяет создать пользователя без открытой регистрации. В локальном auth API администратор создает invite с ролью, сроком действия и лимитом использований, а пользователь принимает ссылку через `/accept-invite`.

23. Что дает отзыв роли или удаление пользователя?
Ответ: В серверной авторизации при изменении роли увеличивается `sessionVersion`, из-за чего старый JWT перестает проходить проверку. Клиент дополнительно проверяет актуальность локальной сессии каждые 15 секунд.

24. Почему анализ видео не размещается на VPS?
Ответ: В текущей архитектуре VPS предназначен для публикации сайта и легкой серверной части авторизации. Видео, OCR, ML и внешние аналитические процессы остаются на локальном ПК, потому что они тяжелые и не нужны для работы публичного интерфейса.

25. Что является источником данных для публичного сайта в текущей версии?
Ответ: Текущая локальная версия использует snapshot/JSON-данные из `src/data/` и локальные ассеты. В коде также есть интеграция Supabase и миграции, но проект имеет переключатель, позволяющий работать без Supabase.

26. Почему в проекте сохранились Supabase-файлы?
Ответ: В репозитории есть `src/integrations/supabase` и `supabase/migrations`, потому что интеграция уже существовала и может быть возвращена позже. При этом локальный сценарий авторизации и данных не обязан обращаться к Supabase.

27. Зачем нужна страница `/docs`?
Ответ: Страница `/docs` описывает API локальной серверной авторизации: health, login, logout, users, invites и accept invite. Она фиксирует, что серверная часть опубликованной версии отвечает за авторизацию, роли и invite-ссылки.

28. Почему проекту важна воспроизводимость данных?
Ответ: Для анализа матчей важно, чтобы одинаковый вход и одинаковая конфигурация давали одинаковые JSON-результаты. В проекте конфигурации вынесены в `scripts/tracking/configs/`, а результаты группируются по имени видео.

29. Что означает архивирование старых модулей?
Ответ: В `scripts/tracking/modules/_archived/` лежат замененные эксперименты и устаревшие модули. Они сохранены для истории и возможного сравнения, но активный пайплайн опирается на текущие модули `find_cuts`, `detect_plates`, `plate_detector`, `recognize_tags`, `hud_read` и `ring_locator`.

30. Почему проект можно считать прикладной аналитической системой?
Ответ: Он объединяет сбор и нормализацию турнирных данных, локальную обработку видео, хранение результатов и web-визуализацию. В нем есть не только интерфейс, но и цепочка подготовки данных для анализа матчей Apex Legends.

Раздел 2. Технические вопросы - 50

31. Где находится основной код web-интерфейса?
Ответ: Основной код web-интерфейса находится в папке `src/`. В ней лежат маршруты `src/routes`, компоненты `src/components`, локальные данные `src/data`, библиотеки `src/lib` и стили `src/styles.css`.

32. Как запускается сайт локально?
Ответ: В `package.json` команда `bun run dev` вызывает PowerShell-скрипт `./dev/start-site-dev.ps1`. Этот скрипт переходит в корень проекта и запускает `bun run dev:vite`, а `dev:vite` запускает `vite dev --config vite.dev.config.ts`.

33. На каком порту по умолчанию открывается сайт?
Ответ: В README указано, что сайт открывается на `http://localhost:8080`. Конкретный запуск выполняется через Vite и конфигурацию `vite.dev.config.ts`.

34. Какой пакетный менеджер используется для проекта?
Ответ: В проекте используется Bun: есть `bun.lock`, скрипты запуска ориентированы на `bun`, а README предлагает `bun install` и `bun run dev`. `npm audit fix --force` для этого проекта не является штатным способом обновления зависимостей.

35. Где находится локальный сервер авторизации?
Ответ: Серверная часть локальной авторизации находится в `server/local-auth-api.mjs`. Для разработки также есть `dev/local-auth-server.ts`, а публичная документация API реализована в маршруте `src/routes/docs.tsx`.

36. Где хранится база локальной авторизации?
Ответ: По умолчанию сервер авторизации хранит данные в JSON-файле `./data/local-auth.json`. Путь можно переопределить переменной окружения `AUTH_DB_PATH`.

37. Какой пользователь создается по умолчанию?
Ответ: При первом запуске локальный auth API создает администратора `admin@apex.local` с паролем `admin12345`. Это видно в `server/local-auth-api.mjs`, где заданы `DEFAULT_ADMIN_EMAIL` и `DEFAULT_ADMIN_PASSWORD`.

38. Как хешируются пароли в серверной авторизации?
Ответ: Пароли хешируются через `pbkdf2Sync` с SHA-256, солью и 120000 итерациями. В JSON-базе хранится соль и хеш, а не исходный пароль.

39. Как устроена серверная сессия?
Ответ: После входа сервер подписывает JWT алгоритмом HS256 и кладет его в cookie `apex_local_auth`. Cookie имеет `HttpOnly`, `SameSite=Lax`, `Path=/`, `Max-Age`, а флаг `Secure` включается по умолчанию, если не отключен переменной окружения.

40. Как реализовано немедленное ограничение доступа после смены роли?
Ответ: У пользователя есть поле `sessionVersion`. При смене роли оно увеличивается, а `verifyJwt` сравнивает версию из токена с актуальной версией пользователя, поэтому старый токен становится недействительным.

41. Как часто клиент проверяет локальную сессию?
Ответ: В `src/lib/auth.tsx` задано `LOCAL_SESSION_CHECK_MS = 15_000`. Это означает, что при локальной авторизации клиент опрашивает `/api/local-auth/me` каждые 15 секунд.

42. Какие роли поддерживаются в проекте?
Ответ: Поддерживаются роли `user`, `operator` и `administrator`. Их порядок задан как `user: 1`, `operator: 2`, `administrator: 3`, а проверка выполняется через функцию `hasAtLeast`.

43. Какая роль нужна для входа в админку?
Ответ: Маршрут `/admin` обернут в `RouteGuard min="operator"`, поэтому для доступа нужна роль `operator` или `administrator`. Страница пользователей в админке дополнительно показывается только администратору.

44. Какие API-методы есть у локального auth API?
Ответ: В `/docs` перечислены методы `/api/local-auth/health`, `/me`, `/login`, `/logout`, `/users`, `/users/role`, `/users/delete`, `/invites`, `/invites/delete`, `/invites/lookup` и `/invites/accept`. Они отвечают за сессии, пользователей и invite-ссылки.

45. Где в коде включается или отключается Supabase?
Ответ: Переключатель находится в `src/lib/runtime-config.ts`. Переменная `VITE_SUPABASE_ENABLED` считается выключенной, если равна `0`, `false`, `off`, `no` или `disabled`.

46. Что происходит, если Supabase отключен?
Ответ: `AuthProvider` использует локальную авторизацию: либо browser-mode через localStorage, либо API-mode через `/api/local-auth`. В этом режиме вход, выход и получение текущего пользователя не обращаются к Supabase.

47. Что такое browser auth mode?
Ответ: Это режим `VITE_AUTH_MODE=browser`, при котором пользователи, invite-ссылки и сессия хранятся в `localStorage` браузера. Он полезен как упрощенный локальный режим, но серверный API-mode надежнее для разных браузеров и VPS.

48. Где находится список публичных маршрутов?
Ответ: Активный dev-router описан в `src/dev-router.tsx`. В нем подключены маршруты `/`, `/login`, `/docs`, `/accept-invite`, `/tournaments`, `/teams`, `/matches`, `/maps`, `/games` и вложенные админские маршруты.

49. Какие админские разделы есть в текущем активном router?
Ответ: В `src/dev-router.tsx` подключены админские маршруты index, dataset, diagrams, hsv, maps, matches, minimap, poi, polygons, processes, schema, teams, tournaments, tracking-lab, users и zones. При этом наличие файла маршрута само по себе не означает, что он отображается в меню.

50. Как устроено меню админки?
Ответ: В `src/routes/admin.tsx` меню разделено на группы Data, Calibration и Analysis. Отдельно есть Dashboard и Users, причем Users показывается только при роли `administrator`.

51. Какие разделы входят в группу Data в админке?
Ответ: В группе Data указаны Tournaments, Matches, Maps и Teams. Они используются для управления сериями, событиями, матчами, картами, командами, составами и цветами.

52. Какие разделы входят в группу Calibration?
Ответ: В Calibration входят HSV, HUD Zones, Map Polygons и POI Zones. Эти разделы связаны с калибровкой цветов команд, зон интерфейса, областей карты и точек интереса.

53. Какие разделы входят в группу Analysis?
Ответ: В Analysis входят Processes, Minimap Locator, Tracking Lab и Dataset Builder. Эти разделы связаны с обработкой видео, проверкой трекинга и подготовкой датасета.

54. Где лежат snapshot-данные ALGS?
Ответ: Основной snapshot лежит в `src/data/algs-bundle.snapshot.json`. Дополнительно есть `src/data/algs-team-rosters.snapshot.json` и `src/data/algs-team-weapons.snapshot.json` для карточек команд.

55. Как сайт получает изображения карт?
Ответ: В `src/lib/algs-snapshot.ts` snapshot-карты связываются с локальными импортами WebP-карт из `src/assets/maps`. Это позволяет показывать карты без загрузки с внешнего источника.

56. Где находятся локальные фотографии игроков?
Ответ: Фотографии игроков лежат в `public/player-images/` в формате WebP. Соответствие файлов и данных описывается через `src/data/player-images.manifest.json`.

57. Как тестовые матчи исключаются из публичной статистики?
Ответ: В `src/lib/public-data.ts` функция `isTestMatchId` считает тестовыми `m-test` и все id, начинающиеся с `m-test`. Функция `publicMatches` фильтрует такие матчи из публичных списков.

58. Какие JSON-файлы используются для тестовой игры `m-test-g1`?
Ответ: В `src/data/m-test-g1/` есть `tracks.json`, `tracks.slots.json`, `slot-to-tag.json`, `rings.json`, `ring_geometry_v2.json`, `hud_timeline.json` и `eliminations.json`. Эти файлы используются для демонстрации обработанной игры.

59. Что хранится в `tracks.json`?
Ответ: По документации Tracking Lab, `tracks.json` содержит `meta` и массив `frames`. В кадрах описывается время, индекс кадра, параметры камеры и треки команд с координатами в мире, на канонической карте и в кадре.

60. Какие состояния может иметь трек команды?
Ответ: В документации указаны состояния `alive`, `low_conf` и `lost`. Они позволяют интерфейсу отличать уверенно найденную команду от низкой уверенности и временной потери.

61. Где находится схема для tracks?
Ответ: В активной структуре tracking указана папка `scripts/tracking/shared/schema/`, а в репозитории есть `scripts/tracking/shared/schema/tracks.schema.json`. Она нужна для формализации структуры выходного JSON.

62. Где находятся конфигурации tracking-пайплайна?
Ответ: Общие конфигурации находятся в `scripts/tracking/configs/`, а конфигурации plate detector - в `scripts/tracking/configs/plate_detector/`. Такой подход позволяет не разносить настройки по разным модулям.

63. Как группируются результаты обработки конкретного видео?
Ответ: По README tracking, если выходной путь не передан явно, активные wrapper-скрипты создают папку по stem имени видео. Например, `game_5.mp4` пишет результаты в `scripts/tracking/matches/game_5/`.

64. Где находится интегрированный plate detector?
Ответ: Бывший отдельный проект `plate_detector` сейчас лежит внутри `scripts/tracking/modules/plate_detector/`. Для запуска из tracking используется wrapper `scripts/tracking/run_plate_detector.ps1`.

65. Какая команда запускает интегрированный plate detector?
Ответ: В README указана команда `.\run_plate_detector.ps1 -Video modules\plate_detector\videos\<vod>.mp4 -SyncToUi`. Через dev-скрипты аналогично можно запускать `.\dev\analyze_plate_detector.ps1 -Video scripts\tracking\game_5.mp4 -SyncToUi`.

66. Что делает `-SyncToUi` в контексте tracking?
Ответ: Согласно README, после обработки `modules/plate_detector/sync_to_ui.py` копирует выбранные JSON/report-артефакты в `src/data/<game>/`. Это связывает локальный пайплайн с web-интерфейсом.

67. Какие этапы входят в текущий run order tracking?
Ответ: Порядок описан так: `find_cuts`, затем `detect_plates` или `plate_detector`, затем `recognize_tags`, затем `hud_read`, затем `ring_locator`, затем `scripts/postprocess/*`, затем `hud_read/sync_to_ui.py`. Web-приложение зависит от финальных JSON, а не от промежуточных модулей.

68. Какие модули tracking архивированы?
Ответ: В README перечислены `detect_teams`, `debug_register`, `motion_detect`, `ocr_tags`, `paddle_ocr_test` и `track_teams`. Они сохранены в архиве как замененные эксперименты или устаревшие реализации.

69. Для чего нужен модуль `find_cuts`?
Ответ: Он отвечает за поиск смен камеры или нарезок в VOD. В активном порядке обработки это первый этап, после которого можно анализировать отдельные фрагменты и кадры.

70. Для чего нужен модуль `recognize_tags`?
Ответ: Он отвечает за извлечение crop-изображений тегов и область обучения/инференса CNN по тегам. В папке модуля есть `extract_crops.py`, `train_classifier.py`, `requirements-ml.txt` и PowerShell-скрипты запуска.

71. Для чего нужен модуль `ring_locator`?
Ответ: Он преобразует данные о кольцах в геометрию на канонической карте. В проекте также есть JSON-файлы `rings.json` и `ring_geometry_v2.json`, которые используются MatchViewer.

72. Что делает `scripts/postprocess/apply_slot_tags.py`?
Ответ: По названию и месту в pipeline этот скрипт относится к постобработке результатов и применению тегов к слотам. Он запускается после основных этапов детекции и распознавания, чтобы очистить или связать итоговый `tracks.json`.

73. Где находится локальная SQLite-база ALGS?
Ответ: В README ALGS API указан путь по умолчанию `scripts/algs_api/data/algs.sqlite`. Этот файл находится в data-папке скриптов и используется как локальная база для синхронизации и кэширования данных API.

74. Какие компоненты есть в ALGS API integration?
Ответ: В `scripts/algs_api/README.md` перечислены `client.py`, `db.py`, `sync.py`, `export_poi_zones.py` и `build_poi_hints.py`. Они отвечают за HTTP-клиент, SQLite-схему, CLI-синхронизацию и экспорт вспомогательных данных.

75. Что делает `client.py` в ALGS API integration?
Ответ: README описывает его как throttled HTTP client с token bucket, jittered backoff и on-disk JSON cache. Он оборачивает публичные read endpoints, которые использует проект.

76. Что делает `sync.py`?
Ответ: `sync.py` - это CLI, который проходит по API и делает upsert данных в SQLite. Он поддерживает команды `reference`, `all`, `season`, `event`, `series`, `standings`, `cc`, `upcoming`, `live` и `refresh`.

77. Как проект защищается от частых запросов к ALGS API?
Ответ: В README указаны три слоя: token-bucket throttle, HTTP cache на диске и таблица `sync_state` как freshness gate. Это позволяет не дергать повторно недавно синхронизированные ресурсы.

78. Какие данные ALGS API не предоставляет?
Ответ: README прямо указывает, что API не предоставляет per-kill feed, per-player damage на уровне матча и старые годы ALGS Year 1-4 через `GET /v1/seasons`. Для старых турниров предусмотрен fallback через Liquipedia scraper.

79. Где находится Liquipedia scraper?
Ответ: Скрипты находятся в `scripts/scrape_liquipedia/`: там есть `scrape.py`, `upload.py`, `build_poi_hints.py`, `requirements.txt` и README. В ALGS README сказано, что Liquipedia используется как fallback для non-ALGS events.

80. Как выполняется production-сборка?
Ответ: В README указана команда `bun x vite build --config vite.dev.config.ts`. Готовая статическая сборка появляется в `dist/`, а папка сборки не должна коммититься.

Раздел 3. Вопросы по выбранному стеку - 10

81. Почему для web-интерфейса используется React?
Ответ: React используется как основной UI-фреймворк, что видно по зависимостям `react`, `react-dom` и JSX/TSX-компонентам в `src/components` и `src/routes`. Проекту нужны интерактивные страницы, фильтры, графики, таблицы и админские формы, для чего компонентная модель React подходит.

82. Зачем проекту Vite?
Ответ: Vite используется как dev-server и build-инструмент. В `package.json` команды `dev:vite` и build-команды запускают Vite, а конфигурация разработки вынесена в `vite.dev.config.ts`.

83. Зачем используется TanStack Router?
Ответ: TanStack Router отвечает за маршрутизацию страниц. В проекте есть file-route модули в `src/routes`, а активный dev-router создает route tree для пользовательских и административных маршрутов.

84. Где используется TanStack Query?
Ответ: В `src/dev-router.tsx` создается `QueryClient`, который передается в context router. Это подготавливает приложение к работе с кэшированием запросов и асинхронными данными в стиле TanStack Query.

85. Почему TypeScript выбран для web-части?
Ответ: Проект написан на `.ts` и `.tsx`, а в зависимостях есть `typescript` и типы React/Node. TypeScript помогает описывать структуры данных, роли, компоненты и функции загрузки данных более явно, чем обычный JavaScript.

86. Для чего используется Tailwind CSS?
Ответ: Tailwind CSS используется для стилизации через utility-классы в компонентах. В `package.json` есть `tailwindcss` и `@tailwindcss/vite`, а в коде много классов вида `bg-background`, `text-muted-foreground`, `border-border`, `px-4`, `text-xs`.

87. Зачем подключены Radix UI компоненты?
Ответ: В зависимостях есть набор `@radix-ui/react-*`, а в `src/components/ui/` находятся обертки для dialog, dropdown-menu, tabs, tooltip, select, scroll-area и других элементов. Это дает готовые доступные UI-примитивы для админки и интерфейса.

88. Для чего используется Recharts?
Ответ: `recharts` присутствует в зависимостях и применяется для графического отображения статистики. В проекте есть страницы команд с графиками, а Tracking Lab также описывает графики по времени.

89. Почему для видеоаналитики используется Python?
Ответ: В `scripts/tracking` и `scripts/algs_api` лежат Python-скрипты и `requirements.txt`. Python выбран для локальной обработки, потому что пайплайн опирается на CV/ML-задачи, работу с видео, JSON, SQLite и внешними API.

90. Для чего в проекте нужен SQLite?
Ответ: SQLite используется локально в `scripts/algs_api/data/algs.sqlite` для синхронизации и нормализации ALGS-данных. Это файловая база, которая подходит локальным скриптам и не требует отдельного сервера.

Раздел 4. Вопросы комиссии о том, чего нет в проекте, но могло бы быть - 10

91. Есть ли в проекте полноценная PostgreSQL-база для текущего локального сайта?
Ответ: В текущей локальной версии основной сценарий опирается на JSON/snapshot-данные и локальный auth JSON-файл. В репозитории есть Supabase-интеграции и миграции, но утверждать, что PostgreSQL является рабочей основной базой текущего локального запуска, нельзя.

92. Есть ли автоматическая обработка загруженного пользователем видео прямо на сайте?
Ответ: В текущем проекте web-интерфейс потребляет уже сгенерированные JSON-артефакты. Загрузка видео и реальный запуск OCR/ML из браузера или с VPS не реализованы как единый production-процесс.

93. Есть ли очередь фоновых задач для анализа видео?
Ответ: Отдельной очереди задач вроде Celery, BullMQ или серверного job-runner в проекте не видно. Аналитические скрипты запускаются локально через PowerShell и Python, а результаты затем копируются в структуру данных сайта.

94. Есть ли централизованный backend для статистических данных сайта?
Ответ: В текущем состоянии backend полноценно реализован для авторизации, ролей и invite-ссылок. Данные турниров, команд, матчей и игр в локальном сценарии берутся из snapshot/JSON-файлов, а не из единого серверного API.

95. Есть ли интеграция real-time обновлений через WebSocket?
Ответ: В проекте не видно WebSocket-слоя для live-обновлений интерфейса. Для авторизации используется периодическая проверка сессии каждые 15 секунд, а не push-уведомления от сервера.

96. Есть ли полноценный audit log действий администратора?
Ответ: В локальном auth API есть операции создания пользователей, смены ролей, удаления и invite-ссылок, но отдельного журнала аудита действий администратора в коде не видно. Такой журнал можно добавить позже как отдельную таблицу или JSON-log.

97. Есть ли двухфакторная аутентификация?
Ответ: Двухфакторной аутентификации в текущей реализации нет. Реализован вход по email и паролю, хранение сессии через JWT в cookie и разграничение прав по ролям.

98. Есть ли автоматические тесты для frontend и tracking-пайплайна?
Ответ: В `package.json` нет отдельной команды `test`, а в структуре проекта не видно выделенного набора unit/e2e-тестов. Проверка сейчас больше опирается на ручной запуск, сборку, тестовые JSON-матчи и визуальный просмотр страниц.

99. Есть ли контейнеризация проекта через Docker?
Ответ: В корне проекта не видно Dockerfile или docker-compose как основного способа запуска. Локальный запуск описан через Bun, PowerShell-скрипты и Python virtual environment для tracking.

100. Есть ли полноценный механизм версионирования результатов анализа матчей?
Ответ: В требованиях и структуре данных есть идея сохранять конфигурацию вместе с результатами, а папки результатов группируются по имени видео. Но отдельного полноценного механизма версий прогонов с историей изменений и сравнением запусков в текущем коде не видно.
