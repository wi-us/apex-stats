# Обоснование выбора инструментов разработки web-части

## Выбор Next.js и React для разработки пользовательского интерфейса

В качестве технологической основы web-части проекта были выбраны `React` и `Next.js`. Такое решение обусловлено спецификой предметной задачи: система представляет собой не статический сайт, а интерактивный аналитический интерфейс с большим количеством взаимосвязанных состояний и пользовательских сценариев.

Во-первых, интерфейс проекта включает сложную синхронизацию данных и отображений: выбор турнира, матча и карты, обновление временного курсора (`timeCursor`), синхронизацию карты с видеоплеером и графиками параметров камеры. В данной конфигурации компонентная модель `React` позволяет естественно организовать приложение как набор переиспользуемых блоков (`viewer`, `map player`, `timeline charts`, `admin`-панели), а также централизовать управление состоянием через hooks и типизированные структуры данных.

Во-вторых, `Next.js` предоставляет удобную архитектуру маршрутизации и сборки страниц в рамках единого приложения. Для проекта это важно, поскольку существуют как пользовательские страницы просмотра, так и специализированные административные режимы (например, CAMERA, HSV, ZONES, POLYGONS). Использование `Next.js` упростило разделение экранов по маршрутам, ускорило локальную разработку и обеспечило готовую основу для дальнейшего промышленного развертывания.

В-третьих, выбранный стек хорошо сочетается с TypeScript-подходом проекта. Для системы, оперирующей большим количеством доменных сущностей (карты, команды, треки, кольца, параметры камеры, конфигурации), строгая типизация существенно снижает число ошибок на стыке frontend и backend API и повышает поддерживаемость кода.

Таким образом, выбор `React` и `Next.js` является технически обоснованным: он обеспечивает требуемую интерактивность, модульность, удобство сопровождения и масштабируемость интерфейса аналитической системы Apex Stats Parser.

## Краткий вывод для раздела ВКР

`React` выбран как библиотека для построения сложного интерактивного интерфейса с большим количеством взаимосвязанных состояний, а `Next.js` — как фреймворк, обеспечивающий структурированную маршрутизацию, удобный процесс разработки и готовность к production-эксплуатации. В совокупности этот стек позволил реализовать удобный web-инструмент для тренерской аналитики и сохранить потенциал дальнейшего развития продукта.

## Значимые технологии (расширенное обоснование)

### 1) Next.js + React (frontend)

Эта связка выбрана как основа пользовательского интерфейса, потому что проект содержит сложную state-логику: выбор турнира/матча/карты, синхронизацию `timeCursor`, совместную работу карты, графиков и видео, а также отдельные admin-режимы. Компонентная модель React и маршрутизация Next.js позволяют развивать интерфейс как модульную систему, а не как набор изолированных страниц.

### 2) TypeScript (единый типизированный контур)

TypeScript используется в web, API и shared-пакете. Для доменных сущностей проекта (карты, кольца, треки команд, камера, конфиги) это особенно важно: типы уменьшают ошибки на стыке frontend/backend, упрощают рефакторинг и повышают предсказуемость поведения системы.

### 3) NestJS (backend API)

NestJS выбран как серверный фреймворк из-за модульной архитектуры, удобной структуры controller/service и хорошей интеграции с валидацией и Swagger. Это позволяет поддерживать map-centric API и одновременно развивать проект в сторону более строгой архитектуры (разделение Catalog/Telemetry/Config в будущем).

### 4) Python + OpenCV/Numpy (видеоаналитика и CV)

Критическая часть проекта связана с обработкой кадров, детекцией карты/колец, оценкой движения камеры и формированием треков. Эти задачи естественно решаются в Python-экосистеме, где OpenCV и Numpy дают наиболее зрелый и производительный инструментарий.

### 5) PostgreSQL + SQLite (гибрид хранения)

В проекте используется смешанная модель хранения: PostgreSQL как целевой canonical-слой и SQLite/JSON как ingestion/fallback-артефакты. Такой подход позволяет одновременно поддерживать исследовательскую гибкость и постепенный переход к более строгой продакшен-модели данных.

### 6) yt-dlp + ffmpeg (получение и подготовка VOD)

Продукт опирается на анализ записей трансляций, поэтому надежный контур загрузки и нарезки видео — базовая часть технологического стека. `yt-dlp` и `ffmpeg` обеспечивают воспроизводимую подготовку исходных данных для последующего анализа.
