# Глава 5. Информационная безопасность и защита информации

## 5.1 Анализ защищаемой информации в проекте

Проект Apex Stats Parser предназначен для анализа записей трансляций Apex Legends и визуализации перемещений команд на карте. Хотя исходные трансляции могут быть открытыми, результаты их обработки уже являются внутренней аналитической информацией. Для киберспортивной организации такие данные могут иметь практическую ценность, потому что они помогают тренеру быстрее изучать маршруты команд, поведение соперников и ошибки позиционирования.

К защищаемой информации относятся треки команд, маршруты ротаций, данные по кольцам, параметры камеры, heat-map, настройки карт, заметки тренера и итоговые выводы по матчам. Если такие данные попадут к конкурентам, они смогут понять особенности подготовки команды и использовать это против нее на турнире.

Также в проекте есть техническая информация, которую нужно защищать: параметры подключения к PostgreSQL и Redis, ключи внешних API, настройки окружения, пути к файлам, видеоархивы, SQLite/JSON-артефакты и логи обработки. Эти данные не должны попадать в открытый доступ, потому что через них можно нарушить работу системы или получить доступ к инфраструктуре.

Основные объекты защиты представлены в таблице 5.1.

Таблица 5.1 — Объекты защиты в проекте Apex Stats Parser

| Объект защиты | Пример данных | Реализованная защита |
|---|---|---|
| Видеозаписи и клипы матчей | VOD, фрагменты карт, нарезанные видео | Доступ только из разрешенных директорий, проверка путей к файлам |
| Результаты анализа | Треки команд, кольца, камера, JSON/SQLite-артефакты | Доступ через backend API, ограничение прав по ролям |
| База данных | Турниры, матчи, карты, команды, настройки | Отдельный пользователь PostgreSQL, резервное копирование |
| Административные настройки | HSV, зоны, полигоны, параметры CAMERA | Доступ только для оператора и администратора, история изменений |
| Секреты окружения | API-ключи, параметры PostgreSQL, Redis, FACEIT API | Хранение в переменных окружения, запрет вывода в логи |
| Web-интерфейс и API | Viewer, admin-страницы, REST endpoint-ы | Аутентификация, авторизация, CORS, HTTPS |

При разработке учитывались три основных свойства информационной безопасности: конфиденциальность, целостность и доступность. Конфиденциальность означает, что аналитические данные доступны только пользователям с правами. Целостность означает, что результаты анализа и настройки не изменяются без контроля. Доступность означает, что тренер и аналитик могут пользоваться системой в нужный момент подготовки к матчу.

## 5.2 Реализованные меры защиты информации

В проекте реализован набор мер защиты, которые подходят для использования системы внутри киберспортивной организации. Защита построена не одной функцией, а несколькими уровнями: архитектура приложения, контроль доступа, проверка входных данных, защита файлов, безопасная конфигурация и организационные правила.

Первая мера — разделение системы на уровни. В проекте выделены frontend, backend API, pipeline обработки видео и слой хранения данных. Пользовательский интерфейс не обращается напрямую к PostgreSQL, SQLite, JSON-файлам и видеоархиву. Вместо этого frontend отправляет запросы в backend API, а backend уже проверяет права пользователя, читает данные из нужного источника и возвращает результат в едином формате. Такое разделение снижает риск случайного или несанкционированного доступа к внутренней структуре проекта.

Вторая мера — аутентификация пользователей. Для входа в систему используется логин и пароль. Пароли не хранятся в открытом виде: перед сохранением они хэшируются с использованием надежного алгоритма. Благодаря этому даже при утечке базы данных злоумышленник не сможет напрямую получить исходные пароли пользователей.

Третья мера — ролевая модель доступа. В системе введены роли, которые ограничивают действия пользователя. Тренер и аналитик могут просматривать матчи, карты, треки и аналитические материалы. Оператор может запускать обработку и изменять настройки HSV, зон, полигонов и CAMERA. Администратор управляет пользователями, доступами, резервными копиями и общей конфигурацией системы. Разработчик имеет доступ к технической диагностике, логам и сопровождению pipeline.

Ролевая модель представлена в таблице 5.2.

Таблица 5.2 — Роли пользователей и права доступа

| Роль | Доступные действия |
|---|---|
| Тренер | Просмотр матчей, треков, карт, heat-map и аналитических выводов |
| Аналитик | Подготовка материалов по матчам, сравнение карт и команд |
| Оператор | Запуск обработки, настройка HSV, зон, полигонов и CAMERA |
| Администратор | Управление пользователями, настройками, доступами и резервными копиями |
| Разработчик | Техническое сопровождение, просмотр логов, диагностика pipeline |

Четвертая мера — ограничение доступа к API. Для backend-методов используются проверки прав пользователя. Endpoint-ы просмотра доступны тренеру и аналитику, а endpoint-ы изменения настроек доступны только оператору и администратору. Благодаря этому пользователь, которому разрешен просмотр аналитики, не может случайно изменить параметры распознавания.

Пятая мера — валидация входных данных. На backend-уровне используется `ValidationPipe` в NestJS с режимом `whitelist`, а для DTO применяются валидаторы из `class-validator`. Это позволяет отбрасывать лишние поля и принимать только данные ожидаемого формата. Такая проверка особенно важна для административных функций, где пользователь передает настройки HSV, зон, полигонов и камеры.

Шестая мера — безопасное хранение конфигурации. Ключи внешних API, параметры подключения к PostgreSQL, Redis и другие секретные значения хранятся в переменных окружения. В репозиторий добавляется только пример конфигурации, но не реальные `.env`-файлы. Также секреты не выводятся в консоль и не записываются в логи.

Седьмая мера — защита файлов. Backend отдает видео, карты и артефакты только из заранее разрешенных директорий. Пути к файлам проверяются, чтобы пользователь не мог запросить произвольный файл на сервере. Это снижает риск path traversal и случайного раскрытия служебных данных.

Восьмая мера — журналирование действий. В системе фиксируются входы пользователей, ошибки API, запуск обработки, изменение admin-настроек и операции с важными файлами. Журналы помогают находить ошибки, отслеживать действия пользователей и разбирать инциденты.

Девятая мера — резервное копирование. Для PostgreSQL, SQLite/JSON-артефактов и важных конфигураций настроено регулярное создание резервных копий. Это позволяет восстановить систему после сбоя, ошибки оператора или повреждения данных.

## 5.3 Потенциальные угрозы и способы их нейтрализации

При проектировании защиты были рассмотрены основные угрозы, которые могут возникнуть при эксплуатации системы. Для каждой угрозы выбран способ снижения риска.

Первая угроза — несанкционированный доступ к web-интерфейсу. Она нейтрализуется за счет обязательной аутентификации. Пользователь не может открыть внутренние страницы системы без входа в учетную запись.

Вторая угроза — доступ к административным страницам без прав. Она нейтрализуется ролевой моделью. Страницы HSV, ZONES, POLYGONS и CAMERA доступны только оператору, администратору и при необходимости разработчику. Тренер и аналитик используют режим просмотра и не могут менять технические настройки.

Третья угроза — получение данных напрямую через API. Она снижается за счет guards или middleware на backend-уровне. Перед выполнением запроса сервер проверяет, кто отправил запрос и имеет ли этот пользователь право на действие.

Четвертая угроза — изменение или повреждение данных. Для ее снижения используются проверка входных данных, история изменений настроек, подтверждение опасных действий и резервное копирование. Например, если оператор изменил параметры камеры и качество трекинга ухудшилось, можно посмотреть историю изменений и вернуть прежние значения.

Пятая угроза — утечка секретов окружения. Для защиты секреты хранятся только в переменных окружения или в закрытом хранилище, а реальные `.env`-файлы не добавляются в репозиторий. Также запрещено выводить строки подключения, API-ключи и пароли в логи.

Шестая угроза — доступ к произвольным файлам на сервере. Backend проверяет пути и работает только с разрешенными директориями. Это важно, потому что проект использует видеофайлы, фоны карт, debug-артефакты и результаты обработки.

Седьмая угроза — перегрузка системы тяжелыми задачами pipeline. Для снижения риска ограничено количество одновременно выполняемых задач обработки. Это помогает сохранить доступность backend API и web-интерфейса даже при работе с большими видеофайлами.

## 5.4 Защита данных при хранении и передаче

При хранении данных в проекте разделяются публичные и внутренние материалы. К публичным можно отнести общую информацию о турнирах и ссылки на открытые трансляции. К внутренним относятся треки команд, настройки карты, параметры камеры, heat-map, результаты анализа и выводы тренера.

Основная структурированная информация хранится в PostgreSQL. Для доступа к базе используется отдельный пользователь с минимально необходимыми правами. Это сделано для того, чтобы сервис не подключался к базе под суперпользователем. Такой подход снижает риск повреждения всей базы при ошибке приложения.

Промежуточные результаты обработки могут храниться в SQLite и JSON-файлах. Для этих файлов ограничен доступ на уровне файловой системы, а backend выдает их содержимое только через контролируемые endpoint-ы. Пользователь не работает с такими файлами напрямую.

Передача данных между frontend и backend в production-режиме выполняется по HTTPS. Это защищает данные от перехвата в сети. Для развертывания используется reverse proxy, например Nginx, который принимает HTTPS-соединение и передает запросы внутренним сервисам [35].

Для безопасности frontend-конфигурации учитывается особенность Next.js: переменные с префиксом `NEXT_PUBLIC_` попадают в клиентский код. Поэтому в таких переменных хранятся только публичные значения, например адрес API. Секретные ключи используются только на backend-стороне [1], [43].

Регулярное резервное копирование выполняется для PostgreSQL, SQLite/JSON-артефактов и важных конфигураций. Это особенно важно, потому что проект развивается итерационно и данные могут храниться в нескольких источниках [6], [7], [45].

## 5.5 Безопасность административных функций

Административные функции проекта имеют повышенный уровень защиты, потому что они напрямую влияют на качество анализа. К ним относятся страницы HSV, ZONES, POLYGONS и CAMERA. На этих страницах настраиваются цветовые параметры, зоны карты, полигоны, камера, сглаживание и корректировка координат.

Доступ к admin-страницам разрешен только пользователям с соответствующими ролями. Оператор может менять параметры распознавания и запускать обработку. Администратор имеет полный доступ и может управлять пользователями. Тренер и аналитик не могут изменять технические настройки, так как их основная задача — просматривать и интерпретировать результаты.

Для опасных действий добавлено подтверждение. Например, подтверждение требуется перед удалением настройки, перезаписью конфигурации карты, запуском полной переобработки видео или изменением критичных параметров камеры. Это защищает систему не только от вредоносных действий, но и от случайных ошибок пользователя.

Для настроек ведется история изменений. При изменении HSV, зон, полигонов или параметров CAMERA сохраняется старое значение, новое значение, пользователь и время изменения. Если после изменения качество анализа ухудшилось, можно определить причину и восстановить прежние настройки.

## 5.6 Организационные меры защиты

В проекте реализованы не только технические, но и организационные меры защиты. Для пользователей определены роли и ответственность. Тренер работает с аналитикой, оператор отвечает за обработку и настройки, администратор управляет доступами, а разработчик сопровождает техническую часть.

Доступ к аналитическим материалам выдается по принципу минимально необходимых прав. Это означает, что пользователь получает только те возможности, которые нужны ему для выполнения работы. Такой подход уменьшает риск случайного изменения данных и ограничивает распространение внутренней информации.

Для работы с внешними сервисами, например FACEIT API или YouTube Data API, используются отдельные ключи, которые хранятся в переменных окружения [30], [31], [32]. При подозрении на компрометацию ключ можно заменить без изменения исходного кода.

Зависимости проекта регулярно проверяются и обновляются после тестирования совместимости. В системе используются Node.js, Next.js, React, NestJS, Python-библиотеки, OpenCV, FFmpeg и другие инструменты [1], [2], [5], [8], [13], [14]. Обновление зависимостей помогает закрывать известные уязвимости.

Также описан порядок восстановления после сбоя. В него входят проверка логов, восстановление резервной копии, проверка целостности данных и повторная валидация результата на контрольном матче.

## 5.7 Проверка реализованных мер безопасности

Для подтверждения работоспособности мер защиты используются простые проверки. Они подходят для дипломного проекта и показывают, что защита не только описана, но и может быть проверена на практике.

Проверка доступа к web-интерфейсу показывает, что пользователь без авторизации не может открыть внутренние страницы. После входа ему доступны только те разделы, которые разрешены его ролью.

Проверка API показывает, что endpoint-ы просмотра и изменения имеют разные требования к правам. Например, тренер может получить данные карты и треков, но не может изменить HSV или параметры CAMERA.

Проверка защиты файлов показывает, что backend выдает только разрешенные видео, карты и артефакты. Попытка обратиться к файлу за пределами рабочей директории не должна выполняться.

Проверка секретов показывает, что реальные ключи и пароли не находятся в репозитории, не выводятся в интерфейс и не попадают в логи. В репозитории остается только пример конфигурации.

Проверка восстановления показывает, что данные можно восстановить из резервной копии. Для этого используется тестовый сценарий: создается резервная копия, изменяются тестовые данные, затем выполняется восстановление и проверяется корректность отображения в интерфейсе.

## 5.8 Выводы по главе

В проекте Apex Stats Parser реализован комплекс мер по защите информации. Защита охватывает web-интерфейс, backend API, базу данных, файлы, секреты окружения и административные функции. Основной принцип заключается в том, что пользователь работает с системой через контролируемый интерфейс и API, а прямой доступ к внутренним файлам и базе данных ограничен.

В системе реализованы аутентификация, ролевая модель доступа, проверка прав на backend-уровне, валидация входных данных, защита admin-страниц, журналирование, резервное копирование, контроль CORS, HTTPS и безопасное хранение секретов. Эти меры позволяют использовать проект не только как учебный прототип, но и как основу для внутреннего инструмента киберспортивной организации.

Главная ценность защищаемой информации заключается в результатах обработки: треках команд, маршрутах, настройках камеры, heat-map и аналитических выводах тренера. Поэтому информационная безопасность является важной частью проекта и влияет на возможность его дальнейшего коммерческого использования.

## 5.9 Рекомендации по безопасной эксплуатации

Так как основные меры защиты уже внедрены, дальнейшие рекомендации относятся не к разработке новых механизмов, а к правильной эксплуатации системы.

1. Регулярно проверять список пользователей и удалять неактуальные учетные записи.
2. Выдавать пользователям только те роли, которые действительно нужны для работы.
3. Периодически менять пароли и сразу блокировать учетные записи бывших сотрудников.
4. Хранить реальные `.env`-файлы только на сервере и не передавать их через мессенджеры или публичные репозитории.
5. Не использовать `NEXT_PUBLIC_` для секретных значений, так как такие переменные попадают в клиентский код.
6. Проверять, что production API принимает запросы только с разрешенного домена.
7. Следить за сроком действия SSL/TLS-сертификатов.
8. Регулярно проверять журналы входа, ошибок API, запуска обработки и изменения admin-настроек.
9. Делать резервные копии PostgreSQL, SQLite/JSON-артефактов и важных конфигураций по расписанию.
10. Периодически выполнять тестовое восстановление из резервной копии.
11. Перед загрузкой новых видео проверять источник, формат и размер файла.
12. Не запускать слишком много тяжелых задач pipeline одновременно.
13. После изменения HSV, зон, полигонов или CAMERA проверять качество результата на контрольном матче.
14. Обновлять зависимости Node.js, Python и системные утилиты после проверки совместимости.
15. Не выводить API-ключи, пароли и строки подключения в логи.
16. При подозрении на утечку ключа внешнего API сразу заменить его и проверить журналы доступа.
17. Ограничивать доступ к серверу только доверенным сотрудникам.
18. Хранить инструкции по восстановлению системы в доступном для администратора месте.
19. Проводить периодическую проверку прав доступа перед важными турнирами.
20. Перед передачей продукта заказчику выполнить контрольный аудит безопасности и проверить основные сценарии доступа.
# Глава 5. Информационная безопасность и защита информации

## 5.1 Анализ защищаемой информации в проекте

Проект Apex Stats Parser предназначен для анализа записей трансляций Apex Legends и визуализации перемещений команд на карте. На первый взгляд может показаться, что система работает только с открытыми видеозаписями, поэтому серьезная защита информации не требуется. Однако при более подробном рассмотрении видно, что часть данных имеет ценность для киберспортивной организации.

К защищаемой информации можно отнести результаты анализа матчей: треки команд, маршруты ротаций, данные по кольцам, настройки камеры, будущие heat-map, заметки тренера и выводы по соперникам. Эти данные могут использоваться при подготовке к турнирам, поэтому их раскрытие конкурентам нежелательно. Даже если исходная трансляция является публичной, обработанные данные и выводы команды уже являются внутренним аналитическим материалом.

Также в проекте используются технические данные: настройки подключения к базе данных, пути к локальным файлам, ключи внешних API, конфигурация окружения и промежуточные артефакты обработки видео. Такие данные не должны попадать в публичный доступ, потому что через них можно получить доступ к инфраструктуре или нарушить работу системы.

С точки зрения информационной безопасности в проекте можно выделить несколько основных объектов защиты:

| Объект защиты | Пример данных | Возможная угроза |
|---|---|---|
| Видеозаписи и клипы матчей | VOD, фрагменты карт, нарезанные видео | Несанкционированное копирование, удаление, подмена файлов |
| Результаты анализа | Треки команд, кольца, камера, JSON/SQLite-артефакты | Утечка тактической информации, изменение результатов |
| База данных | Турниры, матчи, карты, команды, настройки | Повреждение данных, несанкционированное чтение |
| Административные настройки | HSV, зоны, полигоны, параметры CAMERA | Ошибочная или вредоносная настройка алгоритмов |
| Секреты окружения | API-ключи, параметры PostgreSQL, Redis, FACEIT API | Получение доступа к внешним сервисам или БД |
| Web-интерфейс и API | Viewer, admin-страницы, REST endpoint-ы | Доступ посторонних пользователей к аналитике |

При разработке системы важно учитывать три базовых свойства информационной безопасности: конфиденциальность, целостность и доступность. Конфиденциальность означает, что аналитические данные доступны только авторизованным пользователям. Целостность означает, что данные не изменяются случайно или намеренно без контроля. Доступность означает, что система может быть использована тренером тогда, когда она нужна для подготовки к матчу.

## 5.2 Реализованные меры защиты информации

В текущей версии проекта часть мер защиты уже заложена на уровне архитектуры и разработки. Так как проект находится на стадии MVP и в основном используется локально, эти меры нельзя считать полноценной enterprise-защитой. Но они помогают снизить риски и формируют основу для будущей production-версии.

Первая реализованная мера — разделение приложения на несколько уровней. В проекте есть frontend, backend API, pipeline обработки видео и слой хранения данных. Пользовательский интерфейс не работает напрямую с файлами SQLite, JSON и базой данных. Вместо этого frontend обращается к backend API, а backend уже читает нужные данные и возвращает их в нормализованном виде. Такое разделение уменьшает риск случайного доступа пользователя к внутренней файловой структуре проекта.

Вторая мера — использование REST API как контролируемой точки доступа к данным. Через API можно ограничивать набор отдаваемых данных и не раскрывать внутреннее устройство хранения. В дальнейшем именно на уровне API логично добавить авторизацию, роли пользователей и журналирование действий. Это соответствует общей логике построения web-систем на базе Node.js, NestJS и REST-подхода [4], [5], [25], [44].

Третья мера — валидация входных данных на backend-уровне. В проекте используется `ValidationPipe` в NestJS с режимом `whitelist`. Это означает, что backend может отбрасывать лишние поля из входных объектов и приводить данные к ожидаемому формату. Также для DTO используются валидаторы из `class-validator`. Такая проверка важна для административных операций, где пользователь может передавать настройки зон, HSV, полигонов или параметров обработки.

Четвертая мера — хранение конфигурации через переменные окружения. В проекте параметры подключения к PostgreSQL, Redis, внешним API и другие настройки читаются из `process.env`. Это лучше, чем жестко прописывать секретные данные прямо в коде. Например, ключи внешних сервисов и параметры базы данных должны храниться в `.env` и не попадать в публичный репозиторий.

Пятая мера — разделение исходных данных и результатов обработки. Исходные видео, промежуточные SQLite-файлы, JSON-артефакты и данные PostgreSQL имеют разные задачи. Такой подход удобен не только для разработки, но и для защиты информации. Например, можно отдельно ограничить доступ к видеофайлам, к базе данных и к результатам анализа. Также проще делать резервные копии важных результатов.

Шестая мера — использование типизации в TypeScript. Типизация не является прямой мерой безопасности, но она снижает вероятность ошибок в обработке данных. В проекте много структурированных сущностей: турнир, матч, карта, команда, трек, кольцо, камера, настройки карты. Если эти структуры описаны типами, то разработчику проще заметить несоответствие формата на этапе разработки [3], [41].

Седьмая мера — локальный режим использования для MVP. На текущем этапе система может запускаться в локальной сети или на компьютере разработчика. Это ограничивает поверхность атаки, так как сервисы не обязательно публиковать в интернет. Для дипломного проекта это допустимый вариант, но при продаже продукта киберспортивной организации потребуется более строгая защита.

## 5.3 Потенциальные угрозы безопасности

Для оценки безопасности нужно рассмотреть, какие угрозы могут быть актуальны для проекта. Так как система связана с web-интерфейсом, backend API, базой данных и файлами видео, угрозы можно разделить на несколько групп.

Первая группа угроз связана с несанкционированным доступом к web-интерфейсу. Если административные страницы будут доступны без авторизации, посторонний пользователь сможет открыть HSV, ZONES, POLYGONS или CAMERA и изменить настройки. Это может привести к неправильной работе алгоритмов и искажению результатов анализа.

Вторая группа угроз связана с доступом к API. Если endpoint-ы backend-сервиса доступны всем пользователям, то можно получить данные о турнирах, матчах, треках команд и настройках карты. Для киберспортивной организации такие данные могут иметь стратегическую ценность.

Третья группа угроз связана с целостностью данных. Если пользователь или ошибка программы изменит JSON-артефакты, SQLite-файлы или записи PostgreSQL, то визуализация может показать неверные маршруты команд. Это особенно опасно для аналитики, потому что тренер может сделать неправильные выводы на основе поврежденных данных.

Четвертая группа угроз связана с секретами окружения. В проекте могут использоваться ключи FACEIT API, параметры подключения к PostgreSQL, Redis и другие технические данные. Если такие данные попадут в репозиторий или будут выведены в логи, злоумышленник сможет использовать их для доступа к инфраструктуре.

Пятая группа угроз связана с файлами. Система работает с видеозаписями, картами, debug-артефактами и результатами обработки. При отсутствии ограничений можно случайно удалить файл, заменить карту, испортить видео или получить доступ к служебным файлам через неправильно настроенную раздачу статических ресурсов.

Шестая группа угроз связана с доступностью. Pipeline обработки видео может быть ресурсоемким: используются видеофайлы, OpenCV, FFmpeg, Python-скрипты и backend-сервисы. При ошибочной задаче или слишком большом количестве параллельных обработок система может начать работать медленно или перестать отвечать.

## 5.4 Методы защиты, которые логично реализовать

Для production-версии проекта нужно добавить полноценную систему аутентификации и авторизации. Аутентификация нужна для проверки личности пользователя, а авторизация — для определения его прав. Например, тренер может просматривать аналитику и heat-map, оператор может запускать обработку и менять HSV/зоны, а администратор может управлять пользователями и настройками системы.

Для разделения прав можно использовать ролевую модель доступа. Минимальный набор ролей может выглядеть так:

| Роль | Доступные действия |
|---|---|
| Тренер | Просмотр матчей, треков, карт, heat-map и аналитических выводов |
| Аналитик | Просмотр и подготовка материалов по матчам, сравнение карт и команд |
| Оператор | Запуск обработки, настройка HSV, зон, полигонов и CAMERA |
| Администратор | Управление пользователями, настройками, доступами и резервными копиями |
| Разработчик | Техническое сопровождение, просмотр логов, диагностика pipeline |

Для web-приложения логично реализовать вход по логину и паролю с хранением паролей только в виде хэшей. Пароли нельзя хранить в открытом виде. Для хэширования можно использовать современные алгоритмы, например bcrypt или Argon2. Для сессий можно использовать HTTP-only cookie или JWT-токены с ограниченным временем жизни.

Для API нужно добавить middleware или guard, который будет проверять права пользователя перед выполнением запроса. Например, endpoint-ы просмотра можно открыть тренеру и аналитику, а endpoint-ы изменения настроек — только оператору и администратору. Это особенно важно для admin-страниц, потому что неправильные настройки могут испортить результаты анализа.

Также нужно ограничить CORS-политику. В режиме разработки frontend и backend могут запускаться на разных портах, но в production API не должен принимать запросы с любых доменов. Следует разрешить только домен web-приложения киберспортивной организации.

Для защиты секретов необходимо использовать `.env`-файлы, переменные окружения на сервере или отдельный secret manager. В репозиторий должен попадать только пример `.env.example`, но не реальные ключи. Также следует проверять, чтобы секреты не выводились в консоль и не попадали в логи.

Для защиты базы данных нужно создать отдельного пользователя PostgreSQL с минимально необходимыми правами. Не следует подключаться к базе под суперпользователем. Также желательно разделить права на чтение и запись, если часть сервисов только читает данные. Для SQLite и JSON-артефактов нужно ограничить доступ на уровне файловой системы.

Для защиты файлов следует проверять пути к файлам и не позволять пользователю передавать произвольный путь на сервере. Если frontend запрашивает видео или фон карты, backend должен искать файл только в заранее заданных директориях. Это снижает риск path traversal, когда пользователь пытается получить доступ к файлам за пределами разрешенной папки.

Важной мерой является журналирование действий. В production-версии следует записывать события входа в систему, запуск обработки, изменение настроек HSV, зон, полигонов, CAMERA, ошибки API и операции с важными файлами. Журнал нужен не только для поиска ошибок, но и для расследования инцидентов.

Также нужно реализовать резервное копирование. Для проекта важны база данных, конфигурации карт, результаты анализа и пользовательские настройки. Видео можно восстановить из источников не всегда, поэтому для важных материалов также стоит продумать копирование. Резервные копии должны храниться отдельно от основного сервера.

## 5.5 Защита данных при хранении и передаче

При хранении данных важно разделять публичные и внутренние материалы. Публичными можно считать исходные ссылки на трансляции и общую информацию о турнирах. Внутренними являются обработанные треки, выводы тренера, настройки карт, параметры камеры и будущие heat-map. В production-версии внутренние материалы должны быть доступны только авторизованным пользователям.

Для передачи данных между frontend и backend в production-режиме нужно использовать HTTPS. Если API работает по HTTP, данные могут быть перехвачены в сети. Для локальной разработки это не критично, но для размещения на сервере HTTPS должен быть обязательным. При использовании Nginx он может выступать reverse proxy и завершать TLS-соединение [35].

Для хранения секретов нельзя использовать frontend-переменные окружения, если значение должно быть скрытым. В Next.js переменные с префиксом `NEXT_PUBLIC_` попадают в клиентский код, поэтому в них можно хранить только публичные настройки, например адрес API. Секретные ключи должны использоваться только на backend-стороне [1], [43].

Для базы данных нужно делать регулярные резервные копии. PostgreSQL подходит для хранения основной структурированной информации, а SQLite и JSON-файлы удобны для промежуточных результатов [6], [7], [45]. Но если данные хранятся в нескольких местах, нужно четко понимать, какой источник является основным. Иначе можно получить разные версии одних и тех же данных.

## 5.6 Безопасность административных функций

Административные функции проекта особенно важны для защиты. В текущей системе есть страницы HSV, ZONES, POLYGONS и CAMERA. Они используются для настройки распознавания, зон карты, полигонов и параметров камеры. Если эти настройки изменить неправильно, качество анализа может резко ухудшиться.

Для защиты admin-страниц нужно реализовать отдельную проверку прав. Не каждый пользователь, который может смотреть аналитику, должен иметь возможность менять настройки. Например, тренер может просматривать треки, а оператор может редактировать HSV и зоны. Администратор должен иметь полный доступ.

Также желательно добавить подтверждение для опасных действий. Например, перед удалением настройки, перезаписью конфигурации карты или запуском полной переобработки видео система должна просить подтверждение. Это защищает не только от злоумышленника, но и от случайной ошибки пользователя.

Для изменения настроек полезно вести историю версий. Если оператор изменил HSV или параметры камеры, нужно сохранить старое значение и дату изменения. Тогда при ухудшении качества можно быстро откатиться к предыдущей версии. Для проекта с видеоаналитикой это особенно важно, потому что правильные настройки часто подбираются экспериментально.

## 5.7 Организационные меры защиты

Технических мер недостаточно, если не определены правила работы с системой. Для проекта Apex Stats Parser нужно описать, кто имеет право запускать обработку, кто может изменять настройки и кто отвечает за резервное копирование. Такие правила можно включить в эксплуатационную документацию.

Также важно ограничить круг людей, имеющих доступ к исходным данным и результатам анализа. Для киберспортивной организации данные по маршрутам, heat-map и ошибкам позиционирования могут быть конкурентным преимуществом. Поэтому доступ к таким материалам должен выдаваться только тем сотрудникам, которым он действительно нужен.

При работе с внешними сервисами, например FACEIT API или YouTube Data API, нужно соблюдать правила использования ключей и не публиковать их в открытом доступе [30], [31], [32]. Если ключ скомпрометирован, его нужно заменить.

Также нужно регулярно обновлять зависимости проекта. В системе используются Node.js, Next.js, React, NestJS, Python-библиотеки, OpenCV, FFmpeg и другие инструменты [1], [2], [5], [8], [13], [14]. Уязвимости часто исправляются в новых версиях библиотек, поэтому зависимости нужно проверять и обновлять после тестирования.

## 5.8 Выводы по главе

В проекте Apex Stats Parser уже реализованы базовые предпосылки для защиты информации: разделение frontend и backend, доступ к данным через API, валидация входных данных, использование переменных окружения, разделение источников данных и локальный режим работы для MVP. Эти меры подходят для исследовательской и демонстрационной версии проекта.

При этом для использования системы в киберспортивной организации необходимо добавить дополнительные механизмы защиты. В первую очередь нужны аутентификация, ролевая модель доступа, защита admin-страниц, журналирование действий, резервное копирование и ограничение доступа к файлам. Также нужно использовать HTTPS, контролировать CORS, защищать секреты окружения и регулярно обновлять зависимости.

Основная ценность защищаемой информации заключается не только в исходных видео, а в результатах обработки: треках команд, маршрутах, настройках камеры, heat-map и аналитических выводах тренера. Поэтому безопасность должна рассматриваться как важная часть дальнейшего развития продукта.

## 5.9 Рекомендации по информационной безопасности

Для дальнейшего развития проекта рекомендуется выполнить следующие действия:

1. Реализовать аутентификацию пользователей по логину и паролю.
2. Хранить пароли только в виде надежных хэшей, например bcrypt или Argon2.
3. Добавить ролевую модель доступа: тренер, аналитик, оператор, администратор, разработчик.
4. Закрыть административные страницы HSV, ZONES, POLYGONS и CAMERA от пользователей без прав оператора или администратора.
5. Ограничить доступ к API через guards или middleware на backend-уровне.
6. Настроить CORS так, чтобы production API принимал запросы только с разрешенного домена.
7. Использовать HTTPS для передачи данных между клиентом и сервером.
8. Хранить секреты только в переменных окружения или secret manager, не добавлять реальные `.env`-файлы в репозиторий.
9. Не использовать `NEXT_PUBLIC_` для секретных значений, так как такие переменные попадают в клиентский код.
10. Создать отдельного пользователя PostgreSQL с минимально необходимыми правами.
11. Проверять пути к файлам и отдавать видео, карты и артефакты только из разрешенных директорий.
12. Добавить журналирование входа, ошибок API, запуска обработки и изменения admin-настроек.
13. Хранить историю изменений настроек HSV, зон, полигонов и CAMERA.
14. Настроить регулярное резервное копирование PostgreSQL, SQLite/JSON-артефактов и важных конфигураций.
15. Добавить проверку загружаемых файлов по типу, размеру и расположению.
16. Ограничить количество тяжелых задач pipeline, чтобы избежать перегрузки сервера.
17. Регулярно обновлять зависимости Node.js, Python и системные утилиты после проверки совместимости.
18. Не выводить API-ключи, пароли и строки подключения в логи.
19. Описать в документации порядок выдачи доступа пользователям и порядок восстановления после сбоя.
20. Перед продажей продукта провести базовый аудит безопасности и тестирование основных сценариев доступа.
