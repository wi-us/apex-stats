# Глава 3. Особенности реализации и тестирования

## 3.1 Выбор и обоснование средств реализации

При выборе средств реализации учитывалось, что проект Apex Stats Parser состоит из нескольких разных частей. С одной стороны, нужно обрабатывать записи трансляций и получать данные из видео. С другой стороны, нужно хранить результаты анализа, отдавать их через API и показывать пользователю в удобном web-интерфейсе. Поэтому для проекта был выбран не один инструмент, а набор технологий, каждая из которых решает свою задачу.

Для разработки пользовательского интерфейса были выбраны `React` и `Next.js`. `React` подходит для проекта, потому что интерфейс состоит из большого количества связанных элементов: выбор турнира, выбор матча, карта, список команд, таймлайн, видео и графики камеры. Когда пользователь меняет время на таймлайне, должны обновляться сразу несколько частей страницы. В `React` такие задачи удобно решаются через компоненты и состояние. `Next.js` был выбран как фреймворк для организации страниц, маршрутов и сборки web-приложения. В проекте есть главная страница просмотра и отдельные административные страницы, например CAMERA, HSV, ZONES и POLYGONS, поэтому маршрутизация Next.js хорошо подходит для такой структуры [1], [2], [42], [43].

В качестве основного языка для web-части и backend-части используется `TypeScript`. Его преимущество в том, что он добавляет строгую типизацию поверх JavaScript. Для данного проекта это важно, так как в системе есть много структурированных данных: турниры, матчи, карты, команды, треки, кольца, данные камеры и настройки карты. Если такие данные описаны типами, то проще находить ошибки при разработке и сопровождать код [3], [41].

Backend-часть реализована с использованием `Node.js` и `NestJS`. `Node.js` используется как среда выполнения серверного JavaScript/TypeScript-кода, а `NestJS` дает удобную структуру для построения REST API. В проекте API нужен для того, чтобы frontend мог получать данные о турнирах, матчах, картах, командах, треках, кольцах, камере и настройках. NestJS удобен тем, что разделяет код на контроллеры и сервисы, благодаря чему endpoint-ы и логика обработки данных не смешиваются в одном месте [4], [5], [44].

Для хранения данных используется несколько подходов. `PostgreSQL` рассматривается как основное хранилище структурированных данных, потому что это надежная реляционная СУБД, подходящая для хранения турниров, матчей, карт и телеметрии [6], [45]. При этом в проекте также используется `SQLite`, так как он удобен для локальных артефактов обработки видео и промежуточных результатов [7]. Такой подход оказался удобным на этапе разработки: часть данных можно быстро сохранять в локальные файлы, а затем переносить в более строгую структуру.

Для обработки видео и анализа кадров используется `Python`. Этот язык был выбран из-за большого количества библиотек для компьютерного зрения и обработки данных. Основной библиотекой для работы с изображениями и видео является `OpenCV`. Она позволяет обрабатывать кадры, искать области изображения, работать с цветами и геометрическими признаками [8], [47]. Также применяется `NumPy`, который используется для вычислений и работы с массивами данных [9]. Для распознавания текста в отдельных зонах изображения может использоваться `Tesseract OCR` и Python-обертка `pytesseract` [11], [12].

Для подготовки исходных записей используются инструменты `yt-dlp` и `FFmpeg`. `yt-dlp` применяется для загрузки видеоматериалов, а `FFmpeg` — для работы с видеофайлами, нарезки фрагментов и подготовки записей к дальнейшему анализу [13], [14]. Это важно, потому что система работает не с игровым API, а с видеозаписями трансляций.

Для описания API и тестирования используются дополнительные инструменты. Swagger/OpenAPI помогает документировать endpoint-ы backend-сервиса [25]. Jest и Supertest подходят для проверки серверного кода и API, а Playwright или Selenium могут применяться для проверки пользовательских сценариев в браузере [22], [23], [24]. Диаграммы для ВКР оформляются в Mermaid, так как этот формат позволяет быстро описывать архитектуру, последовательности и схемы процессов в текстовом виде [26].

Таким образом, выбранные средства реализации соответствуют структуре проекта. Frontend реализуется на Next.js и React, backend — на NestJS, обработка видео — на Python и OpenCV, а хранение данных — через PostgreSQL, SQLite и JSON-артефакты. Такой набор технологий не является самым простым, но он позволяет разделить задачи проекта на понятные части.

## 3.2 Особенности реализации

Главная особенность реализации проекта заключается в том, что система объединяет несколько разных процессов: обработку видео, хранение данных, backend API и web-визуализацию. Эти части работают вместе, но выполняют разные задачи.

На первом этапе система получает записи трансляций. Для этого используются скрипты загрузки и синхронизации видео. После получения VOD выполняется обработка, которая определяет карту, временные границы игрового фрагмента, кольца и параметры камеры. Эти данные сохраняются в SQLite и JSON-артефакты. Такой вариант удобен для разработки, потому что можно отдельно проверять результаты каждого шага и не запускать весь проект заново.

Отдельная часть проекта отвечает за построение треков команд. Треки показывают, где команда находилась в конкретный момент времени. Так как данные берутся из трансляции, результат может быть неточным. На качество влияют цветовые настройки, положение камеры, качество видео и особенности HUD. Поэтому в проекте есть административные инструменты для настройки HSV, зон и полигонов.

Backend-часть проекта предоставляет REST API. Через него web-интерфейс получает данные о турнирах, матчах, картах, командах, треках, кольцах и камере. Основная идея API состоит в том, что большая часть данных привязана к конкретной карте. Пользователь выбирает карту, и после этого frontend запрашивает все связанные с ней данные. Такой подход упрощает логику интерфейса.

Важной особенностью frontend является единый временной курсор `timeCursor`. Он нужен для синхронизации карты, таймлайна, графиков и видео. Если пользователь перемещает таймлайн, то меняется отображение команд на карте, обновляются графики и изменяется позиция видео. Благодаря этому тренер может смотреть не просто статичную картинку, а состояние матча в конкретный момент времени.

Для отображения карты и треков используется Canvas. Это удобно, потому что на карте нужно рисовать много элементов: фон карты, точки команд, линии треков, кольца, подписи и служебную информацию. Canvas позволяет управлять отрисовкой вручную и обновлять изображение при изменении времени.

Отдельное внимание в реализации уделено странице CAMERA. Она нужна для проверки и настройки трекинга камеры. На этой странице рядом отображаются карта и видеоплеер, а ниже находятся графики параметров камеры. Пользователь может сравнить, совпадает ли положение на карте с видео, и изменить параметры сглаживания. Это важно, потому что ошибки камеры могут смещать треки команд.

В проекте реализованы несколько механизмов для улучшения отображения камеры. EMA-сглаживание уменьшает шум в координатах камеры. Anti-latch помогает бороться с длинными ложными смещениями. Pre-jump lock удерживает камеру до подтвержденного реального скачка. Step-shift применяется для корректировки треков после скачков камеры. Эти механизмы добавлялись постепенно, потому что при работе с реальными записями стало видно, что простого сглаживания недостаточно.

Еще одна особенность реализации — fallback-подход к данным. На этапе разработки часть данных может находиться в PostgreSQL, часть — в SQLite, а часть — в JSON-файлах. Backend должен уметь читать данные из разных источников и отдавать frontend результат в одинаковом формате. Такой подход не идеален для большой production-системы, но он удобен для исследовательского проекта и позволяет быстрее проверять гипотезы.

Также важно отметить, что проект развивался итерационно. Сначала была нужна базовая карта и треки команд. Затем появилась необходимость в отдельной CAMERA-странице, настройках сглаживания, синхронизации видео, графиках и admin-инструментах. Поэтому часть кода сейчас можно улучшить архитектурно. Например, большой backend-сервис каталога в будущем лучше разделить на более мелкие сервисы: отдельно каталог, телеметрию, настройки карты и работу с файлами.

## 3.3 Особенности тестирования

Тестирование проекта Apex Stats Parser отличается от обычной проверки web-сайта. Здесь недостаточно проверить, что страница открывается и кнопки нажимаются. Нужно также убедиться, что данные корректно загружаются, треки отображаются на карте, видео синхронизируется с таймлайном, а настройки камеры действительно влияют на результат.

Первый уровень тестирования — проверка API. Нужно убедиться, что backend возвращает данные по основным endpoint-ам: турниры, матчи, карты, команды, треки, кольца, камера, фон карты, видео и настройки. Если API возвращает неправильный формат данных, frontend не сможет корректно построить карту. Для проверки backend-части можно использовать ручные запросы в браузере или инструменты тестирования API. Также для автоматических проверок подходят Jest и Supertest [22].

Второй уровень — проверка пользовательского интерфейса. Нужно открыть web-приложение, выбрать турнир, матч и карту, убедиться, что появились команды и карта. Затем следует проверить работу таймлайна: при изменении времени положение команд должно обновляться. Также нужно проверить кнопки play/pause, выбор скорости воспроизведения и fullscreen-режим. Для browser-тестов в будущем можно использовать Playwright или Selenium [23], [24].

Третий уровень — проверка CAMERA-страницы. Это один из самых важных экранов для контроля качества. На этой странице проверяется, что видео открывается, карта отображается рядом с видео, графики камеры загружаются и курсор времени синхронизирует все элементы. Если пользователь перемещает видео или таймлайн, то карта и графики должны соответствовать этому моменту.

Четвертый уровень — визуальная проверка качества треков. Так как система анализирует видеозаписи, часть ошибок можно заметить только глазами. Например, трек команды может резко «перепрыгнуть» через карту, точка может оказаться не в той области или камера может сместить все координаты. Поэтому часть тестирования выполняется вручную: выбираются несколько таймингов, и результат на карте сравнивается с видео.

Для оценки качества камеры можно использовать несколько простых метрик. `Jitter` показывает, насколько сильно дрожит камера в те моменты, когда реального движения быть не должно. `False unlock count` показывает, сколько раз блокировка камеры снялась раньше реального скачка. `Anti-latch hits` показывает, сколько раз алгоритм исправлял длинный ложный хвост. Также используется визуальная согласованность карты, видео и графиков. Эти метрики не дают абсолютно точной оценки качества, но помогают сравнивать настройки между собой.

Пятый уровень — проверка административных инструментов. Для HSV нужно проверить, что выбранные параметры действительно влияют на распознавание. Для ZONES и POLYGONS нужно проверить, что карта загружается, зоны отображаются и сохраняются. Эти инструменты важны, потому что качество итогового анализа зависит от правильной подготовки карты.

Для приемочного тестирования можно использовать следующий сценарий. Пользователь открывает приложение, выбирает турнир, матч и карту. После этого проверяет, что появились команды, карта и треки. Затем он открывает CAMERA-страницу, включает видео и перемещает таймлайн. Если карта, видео и графики меняются согласованно, базовый сценарий считается выполненным. После этого пользователь меняет параметры камеры и проверяет, что отображение треков действительно меняется.

В результате тестирования нужно получить не только ответ «работает» или «не работает», но и список ограничений. Например, могут быть проблемы с качеством видео, с резкими скачками камеры, с неполными данными по командам или с настройками HSV. Такой список ограничений важен, потому что проект связан с анализом реальных трансляций, где входные данные не всегда одинаковые.

Таким образом, тестирование проекта включает функциональные проверки API, ручную проверку интерфейса, визуальную валидацию треков, проверку CAMERA-страницы и анализ качества камеры. Такой подход позволяет оценить не только техническую работоспособность, но и практическую пригодность системы для тренерского анализа.
